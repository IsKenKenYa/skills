# Crash 故障案例库：踩内存 / UAF

## 一、故障类型

**一级根因：内存破坏 / 踩内存**

**二级根因：Use-After-Free / 越界写 / 栈破坏 / 代码段破坏**

**结论等级：**

| 等级 | 含义 |
|------|------|
| 一定为踩内存 / UAF | 证据强，可直接定性为踩内存或 UAF |
| 可能为踩内存 | 证据中等，需要结合锁保护、对象生命周期、多线程访问等进一步排查 |

---

## 二、一定为踩内存 / UAF 的案例

### Case 1：fault_addr 高位为 0x6b6b 开头

#### 判定条件

满足以下任一条件：

| 证据 | 判定 |
|------|------|
| `fault_addr` 高位为 `0x6b6b` 开头 | 一定为 UAF / 踩内存 |
| 通过汇编和寄存器分析，当前访问地址头部包含 `6b6b` | 一定为 UAF / 踩内存 |

#### 典型特征

```text
fault_addr = 0x6b6bxxxxxxxxxxxx
```

或寄存器中出现：

```text
x0/x1/x2/... = 0x6b6bxxxxxxxxxxxx
```

#### 根因解释

`0x6b6b` 通常是释放后内存填充值或异常填充值特征。当前线程访问了带有 `6b6b` 特征的地址，说明对象大概率已经被释放或被破坏。

#### 结论模板

```text
当前崩溃访问地址包含 0x6b6b 特征，符合释放后内存被访问的典型表现，判定为 UAF / 踩内存。
```

---

### Case 2：崩溃在 jemalloc 分配逻辑中

#### 判定条件

| 证据 | 判定 |
|------|------|
| 崩溃线程栈顶为 `malloc` | 一定为踩内存 |
| 崩溃发生在 jemalloc 分配逻辑中 | 一定为踩内存 |

#### 典型调用栈

```text
#00 malloc
#01 ...
```

或：

```text
#00 je_malloc
#01 malloc
#02 ...
```

#### 根因解释

`malloc / jemalloc` 分配逻辑经过长期验证，一般不认为是分配器内部问题。若崩溃发生在分配器内部，通常是堆结构被提前踩坏，例如越界写、重复释放、UAF 等导致 allocator 元数据损坏。

#### 结论模板

```text
崩溃发生在 jemalloc/malloc 分配逻辑中，malloc 内部逻辑可信，通常说明堆元数据已被破坏，判定为踩内存问题。
```

---

### Case 3：崩溃在 CFI 检查逻辑中

#### 判定条件

| 证据 | 判定 |
|------|------|
| 崩溃线程栈包含 `__cfi_check_fail` | 一定为 UAF / 踩内存 |

#### 典型调用栈

```text
#00 __cfi_check_fail
#01 ...
```

#### 根因解释

CFI 失败通常表示间接调用对象的类型、虚表、函数指针或对象布局异常。常见原因是对象已释放后仍被调用，或对象内存被覆盖，导致 CFI 检查失败。

#### 结论模板

```text
崩溃栈包含 __cfi_check_fail，说明 CFI 检查对象异常，通常是对象 UAF 或对象内存被破坏导致，判定为踩内存 / UAF。
```

---

### Case 4：崩溃在 PAC 逻辑中

#### 判定条件

| 证据 | 判定 |
|------|------|
| 崩溃栈访问的 PC 汇编为 `autibsp` | 一定为栈破坏 / 踩内存 |
| 架构为 arm64，崩溃点位于 PAC 认证逻辑 | 一定为栈破坏 / 踩内存 |

#### 典型汇编

```asm
autibsp
```

#### 根因解释

`autibsp` 是 arm64 PAC 相关指令，通常用于返回地址或栈帧认证。如果在该位置崩溃，常见原因是保存的 `SP / X29 / X30` 被破坏。

#### 结论模板

```text
崩溃发生在 PAC 认证逻辑，PC 汇编为 autibsp，通常表示保存的 SP/X29/X30 已被破坏，判定为栈内存被踩。
```

---

### Case 5：崩溃在 StackProtector 逻辑中

#### 判定条件

| 证据 | 判定 |
|------|------|
| 崩溃线程栈包含 `__stack_chk_fail` | 一定为栈破坏 / 踩内存 |

#### 典型调用栈

```text
#00 __stack_chk_fail
#01 ...
```

#### 根因解释

`__stack_chk_fail` 表示栈保护检查失败，通常是函数栈上的 canary 被改写。常见原因包括栈越界写、局部数组溢出、保存的 `SP / X29 / X30` 被破坏等。

#### 结论模板

```text
崩溃栈包含 __stack_chk_fail，说明 StackProtector 检测到栈保护值被破坏，通常为栈内存越界写或栈帧被破坏，判定为踩内存。
```

---

### Case 6：崩溃在可执行代码段，且 PC dump 与二进制不一致

#### 判定条件

| 证据 | 判定 |
|------|------|
| 崩溃 PC 位于可执行代码段 | 强证据 |
| PC dump 的内存内容与二进制文件对应位置内容不一致 | 一定为代码段被破坏 / 踩内存 |

#### 根因解释

正常情况下，可执行代码段内容应与二进制文件中的代码一致。如果运行时 PC 附近内存与二进制不一致，说明代码段被异常改写，属于严重内存破坏。

#### 结论模板

```text
崩溃发生在可执行代码段，且 PC dump 内容与二进制文件对应代码不一致，说明代码段被异常改写，判定为踩内存问题。
```

## 三、可能为踩内存的案例

### Case 7：崩溃在加锁的容器成员访问

#### 判定条件

同时满足：

| 证据 | 判定 |
|------|------|
| 调用栈顶在 `map / vector / array` 等容器访问逻辑 | 可能为踩内存 |
| 汇编指向访问容器元素 | 可能为踩内存 |
| 该容器访问均已加锁保护 | 排除普通并发访问问题后，倾向踩内存 |

#### 典型场景

```text
std::map::find
std::vector::operator[]
std::array::operator[]
std::__tree
```

#### 根因解释

如果容器访问已被锁保护，普通并发读写导致崩溃的可能性下降。此时若仍在容器元素访问中崩溃，需要怀疑容器对象本身、内部节点、元素对象或迭代器已被破坏。

#### 结论模板

```text
崩溃发生在容器成员访问逻辑，且该容器访问路径已加锁保护，普通并发访问问题可能性较低，当前更倾向于容器对象或元素内存被踩，判定为可能踩内存。
```

---

### Case 8：崩溃在加锁的 shared_ptr 相关逻辑

#### 判定条件

同时满足：

| 证据 | 判定 |
|------|------|
| 调用栈顶在 `shared_ptr` 相关析构 / 引用计数 / 释放逻辑 | 可能为踩内存 |
| `shared_ptr` 的保存、赋值均已加锁保护 | 排除普通并发赋值问题后，倾向踩内存 |

#### 典型调用栈

```text
std::shared_ptr::~shared_ptr
std::__shared_count::~__shared_count
std::__shared_weak_count::__release_shared
```

#### 根因解释

`shared_ptr` 本身的引用计数逻辑通常可靠。如果保存、赋值路径均有锁保护，但仍在析构或引用计数逻辑中崩溃，需要怀疑控制块、对象本体或保存 shared_ptr 的宿主对象被踩坏。

#### 结论模板

```text
崩溃发生在 shared_ptr 相关析构/释放逻辑，且 shared_ptr 的保存、赋值均已加锁保护，普通并发修改可能性较低，当前更倾向于 shared_ptr 控制块或对象内存被破坏，判定为可能踩内存。
```

---

### Case 9：崩溃在 arkJsRuntime 的堆内存中

#### 判定条件

同时满足：

| 证据 | 判定 |
|------|------|
| 崩溃发生在 `arkJsRuntime` 的堆内存中 | 可能为踩内存 |
| 已排除多线程操作 JS 堆对象场景 | 可能为踩内存 |

#### 根因解释

ArkJS Runtime 堆对象通常要求在特定线程或特定运行时上下文中访问。如果已经排除多线程非法操作 JS 堆对象，但仍在 ArkJS Runtime 堆内存中崩溃，需要怀疑 JS 堆对象、运行时对象或关联 native 对象被破坏。

#### 结论模板

```text
崩溃发生在 arkJsRuntime 堆内存中，且已排除多线程操作 JS 堆对象场景，当前更倾向于 JS 堆对象或关联 native 对象被破坏，判定为可能踩内存。
```

## 四、故障案例库汇总表

| Case | 现象 | 关键证据 | 结论 |
|------|------|----------|------|
| 1 | 访问地址包含 `0x6b6b` | `fault_addr` 或寄存器访问地址高位为 `0x6b6b` | 一定为 UAF / 踩内存 |
| 2 | 崩溃在 jemalloc/malloc | 栈顶为 `malloc` 或 jemalloc 分配逻辑 | 一定为踩内存 |
| 3 | CFI 检查失败 | 栈包含 `__cfi_check_fail` | 一定为 UAF / 踩内存 |
| 4 | PAC 认证失败 | PC 汇编为 `autibsp` | 一定为栈破坏 / 踩内存 |
| 5 | StackProtector 失败 | 栈包含 `__stack_chk_fail` | 一定为栈破坏 / 踩内存 |
| 6 | 代码段异常 | PC dump 与二进制内容不一致 | 一定为代码段被踩 |
| 7 | 加锁容器访问崩溃 | map/vector/array 访问，且访问已加锁 | 可能为踩内存 |
| 8 | 加锁 shared_ptr 崩溃 | shared_ptr 保存/赋值均加锁，析构崩溃 | 可能为踩内存 |
| 9 | arkJsRuntime 堆崩溃 | 排除多线程 JS 堆访问后仍崩溃 | 可能为踩内存 |

## 六、精简版判定规则

```text
一定为踩内存 / UAF：
1. fault_addr 或当前访问地址包含 0x6b6b
2. 崩溃在 jemalloc/malloc 分配逻辑
3. 栈包含 __cfi_check_fail
4. PC 汇编为 autibsp
5. 栈包含 __stack_chk_fail
6. PC 位于代码段，且 dump 内容与二进制不一致

可能为踩内存：
1. 崩溃在加锁保护的 map/vector/array 等容器元素访问
2. 崩溃在加锁保护的 shared_ptr 析构/释放/引用计数逻辑
3. 崩溃在 arkJsRuntime 堆内存，且已排除多线程操作 JS 堆对象
```
